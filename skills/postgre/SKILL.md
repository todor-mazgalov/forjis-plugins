# PostgreSQL Schema Design

Design clean, performant, maintainable PostgreSQL schemas. Prioritize data
integrity, appropriate data types, and native PostgreSQL features.

## Before Writing Schema

1. **Understand the domain.** Read existing schema, migrations, and ORM models
   before proposing changes. Know what tables exist and how they relate.
2. **Check the PostgreSQL version.** Look at `docker-compose.yml`, CI config,
   or deployment docs. Version determines which features are available
   (e.g., generated columns since 12, MERGE since 15, identity columns since 10).
3. **Follow project conventions.** Match existing naming style, migration tool
   format, and constraint patterns already in use.

## Naming Conventions

Consistent naming prevents confusion and makes schemas self-documenting.
PostgreSQL folds unquoted identifiers to lowercase, so snake_case is the
natural fit — it avoids quoting and reads clearly.

| Element | Convention | Example |
|---------|-----------|---------|
| Tables | Plural snake_case noun | `orders`, `user_accounts` |
| Columns | Singular snake_case | `created_at`, `email_address` |
| Primary keys | `id` or `<table_singular>_id` | `id`, `order_id` |
| Foreign keys | `<referenced_table_singular>_id` | `customer_id` |
| Indexes | `ix_<table>_<columns>` | `ix_orders_customer_id` |
| Unique constraints | `uq_<table>_<columns>` | `uq_users_email` |
| Check constraints | `ck_<table>_<description>` | `ck_orders_positive_total` |
| Exclusion constraints | `ex_<table>_<description>` | `ex_bookings_no_overlap` |
| FK constraints | `fk_<table>_<referenced_table>` | `fk_orders_customers` |
| Sequences | `<table>_<column>_seq` | `orders_id_seq` |
| Enums | Singular snake_case | `order_status`, `payment_method` |
| Domains | Descriptive snake_case | `email_address`, `positive_amount` |
| Schemas | Short lowercase name | `billing`, `auth`, `public` |

Avoid abbreviations. `customer_id` reads better than `cust_id` and is only
a few characters longer. The schema outlives the typing effort.

## Data Types — Choose Precisely

Choosing the right type is the single most impactful schema decision. The right
type enforces constraints at the storage layer, enables efficient indexing, and
prevents entire classes of bugs that application code would otherwise need to
catch.

### Identity columns

```sql
-- WRONG — serial is legacy syntax
CREATE TABLE orders (
    id serial PRIMARY KEY
);

-- CORRECT — identity columns (PostgreSQL 10+)
CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
);
```

Use `GENERATED ALWAYS AS IDENTITY` for auto-incrementing keys. It's the SQL
standard, prevents accidental manual inserts, and uses `bigint` by default
(which avoids the integer overflow problem that has bitten many production
systems). Reserve `GENERATED BY DEFAULT` only when you need to bulk-import
rows with pre-assigned IDs.

Use UUIDs (`uuid` type with `gen_random_uuid()`) when you need globally unique
IDs, distributed systems, or want to avoid exposing sequential ordering. The
tradeoff is larger key size (16 bytes vs 8) and slightly worse index locality.

### Text

```sql
-- WRONG — varchar(255) cargo-culted from MySQL
name varchar(255) NOT NULL,

-- CORRECT — use text with a check constraint when you need a length limit
name text NOT NULL,
-- or with an explicit limit enforced via constraint
name text NOT NULL CONSTRAINT ck_users_name_length CHECK (length(name) <= 200),
```

PostgreSQL stores `text`, `varchar`, and `varchar(n)` identically — there is
no performance difference. Use `text` by default. Add a `CHECK` constraint
only when you have a genuine business reason for a length limit (e.g., a
country code must be exactly 2 characters). This separates storage concerns
from business rules and makes limits easier to change later (altering a check
constraint doesn't rewrite the table).

### Numeric and money

```sql
-- WRONG — float for money (binary floating point loses precision)
price float NOT NULL,

-- WRONG — the money type (locale-dependent, hard to work with)
price money NOT NULL,

-- CORRECT — numeric with explicit precision for financial values
price numeric(12, 2) NOT NULL,

-- ALSO CORRECT — integer cents to avoid decimals entirely
price_cents integer NOT NULL CONSTRAINT ck_products_positive_price CHECK (price_cents > 0),
```

Use `numeric(precision, scale)` for exact decimal values (money, measurements).
Use `integer` / `bigint` for counts and integer quantities. Use `real` /
`double precision` only for scientific data where approximate values are
acceptable.

### Timestamps

```sql
-- WRONG — timestamp without time zone (ambiguous, timezone bugs)
created_at timestamp DEFAULT now(),

-- CORRECT — timestamptz stores UTC, renders in session timezone
created_at timestamptz NOT NULL DEFAULT now(),
```

Use `timestamptz` (timestamp with time zone) for all temporal data. PostgreSQL
stores it as UTC internally and converts to the session timezone on display.
Plain `timestamp` (without time zone) silently discards timezone information,
causing subtle bugs when servers or clients are in different timezones.

Use `date` for calendar dates without time. Use `interval` for durations.
Use range types (`tstzrange`) when you need to model periods — they integrate
with exclusion constraints for overlap prevention.

### Boolean

```sql
-- WRONG — integer flags
is_active integer DEFAULT 1,

-- CORRECT — native boolean
is_active boolean NOT NULL DEFAULT true,
```

### JSON

```sql
-- WRONG — json type (reparsed on every access)
metadata json,

-- CORRECT — jsonb (binary, indexable, supports operators)
metadata jsonb NOT NULL DEFAULT '{}',
```

Use `jsonb` for semi-structured data. It supports GIN indexes for fast
containment queries (`@>`, `?`, `?|`), path extraction (`->>`, `#>>`), and
partial updates via `jsonb_set()`. Use it for metadata, configuration, audit
trails, and data that varies per row. Do not use it as an excuse to skip
schema design — if structure is known and stable, use proper columns.

### Arrays

```sql
-- Array column for small, fixed sets
tags text[] NOT NULL DEFAULT '{}',
```

Arrays work well for small lists of values that belong to the row and are
queried with `@>`, `&&`, or `ANY()`. They support GIN indexing. For large or
independently-queryable collections, use a separate table with a foreign key.

### Enums vs lookup tables

```sql
-- PostgreSQL enum — good for stable, small sets
CREATE TYPE order_status AS ENUM ('pending', 'confirmed', 'shipped', 'delivered', 'cancelled');

-- Lookup table — better when values change or need metadata
CREATE TABLE order_statuses (
    id smallint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL UNIQUE,
    display_label text NOT NULL,
    is_terminal boolean NOT NULL DEFAULT false
);
```

Use enums when the set is small, stable, and doesn't need metadata. Use lookup
tables when values change over time, need additional attributes, or when you
want to add values without a migration (adding enum values requires `ALTER TYPE`
and cannot be done inside a transaction before PostgreSQL 12).

### Ranges

```sql
-- Model a booking period as a range
valid_during tstzrange NOT NULL,

-- Prevent overlapping bookings for the same room
CONSTRAINT ex_bookings_no_overlap
    EXCLUDE USING gist (room_id WITH =, valid_during WITH &&)
```

Range types (`int4range`, `tstzrange`, `daterange`, etc.) are a powerful
PostgreSQL feature for modeling intervals. Combined with exclusion constraints,
they enforce non-overlap at the database level — no application code needed.

## Constraints — Enforce Integrity in the Database

The database is the last line of defense for data integrity. Application bugs
come and go, but constraints are permanent. Every business rule that can be
expressed as a constraint should be.

### NOT NULL by default

```sql
-- Start with NOT NULL, only allow NULL when the absence of a value
-- has genuine meaning (e.g., optional fields, unknown data)
CREATE TABLE users (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text NOT NULL,
    name text NOT NULL,
    phone text,  -- genuinely optional
    created_at timestamptz NOT NULL DEFAULT now()
);
```

Make columns `NOT NULL` unless you have a specific reason to allow nulls.
NULLs introduce three-valued logic that complicates queries, indexes, and
application code. When a column is optional, document why.

### Foreign keys

```sql
CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL REFERENCES customers(id),
    -- ...
);
```

Every relationship should have an explicit foreign key. Specify `ON DELETE`
behavior explicitly:

| Behavior | Use when |
|----------|----------|
| `RESTRICT` (default) | Parent must not be deleted while children exist |
| `CASCADE` | Children are meaningless without the parent (e.g., order items) |
| `SET NULL` | Children can exist independently (e.g., assigned_to on tasks) |

Avoid `ON DELETE SET DEFAULT` — it's rarely the right choice and can mask bugs.

Index every foreign key column. PostgreSQL does not automatically create indexes
on foreign key columns (unlike some other databases), and without them,
`ON DELETE CASCADE` and joins on the FK become sequential scans.

### Check constraints

```sql
-- Domain rules belong in the schema
CONSTRAINT ck_orders_positive_total CHECK (total > 0),
CONSTRAINT ck_users_email_format CHECK (email ~* '^[^@]+@[^@]+\.[^@]+$'),
CONSTRAINT ck_products_valid_dates CHECK (available_from < available_until),
```

Use check constraints for single-row validations: ranges, formats, cross-column
rules. They're fast, always enforced, and self-documenting.

### Unique constraints

```sql
-- Simple unique
CONSTRAINT uq_users_email UNIQUE (email),

-- Composite unique (an order can have each product only once)
CONSTRAINT uq_order_items_order_product UNIQUE (order_id, product_id),

-- Partial unique (only active users must have unique email)
CREATE UNIQUE INDEX uq_users_active_email ON users (email) WHERE is_active;
```

Partial unique indexes are powerful for "unique among a subset" rules that
`UNIQUE` constraints alone cannot express.

### Exclusion constraints

```sql
-- Prevent overlapping bookings per room
CREATE TABLE bookings (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id bigint NOT NULL REFERENCES rooms(id),
    during tstzrange NOT NULL,
    CONSTRAINT ex_bookings_no_overlap
        EXCLUDE USING gist (room_id WITH =, during WITH &&)
);
```

Exclusion constraints generalize uniqueness — they prevent rows where specified
expressions would conflict according to given operators. The classic use case
is temporal overlap prevention, but they work for spatial data and other domains
too. Requires the `btree_gist` extension for mixing equality with range overlap.

## Indexes — Targeted, Not Blanket

Indexes speed up reads but slow down writes and consume storage. Add indexes
based on actual query patterns, not speculation.

### B-tree (default)

```sql
-- Single column — for equality and range queries
CREATE INDEX ix_orders_customer_id ON orders (customer_id);

-- Composite — column order matters (most selective or equality first)
CREATE INDEX ix_orders_customer_status ON orders (customer_id, status);

-- Covering — includes extra columns to enable index-only scans
CREATE INDEX ix_orders_customer_covering
    ON orders (customer_id) INCLUDE (total, created_at);
```

Composite index column order follows the "equality, then range" principle:
put columns used in `=` conditions first, columns used in range/sort last.
An index on `(a, b, c)` serves queries on `a`, `(a, b)`, and `(a, b, c)`,
but not `b` alone or `(b, c)`.

### Partial indexes

```sql
-- Only index rows that queries actually filter on
CREATE INDEX ix_orders_pending ON orders (created_at) WHERE status = 'pending';
```

Partial indexes are smaller and faster when queries always include a `WHERE`
clause that matches the index predicate. They're especially useful for status
flags where most rows are in a terminal state.

### GIN (Generalized Inverted Index)

```sql
-- Full-text search
CREATE INDEX ix_articles_search ON articles USING gin (to_tsvector('english', body));

-- JSONB containment queries
CREATE INDEX ix_events_metadata ON events USING gin (metadata);

-- Array containment
CREATE INDEX ix_posts_tags ON posts USING gin (tags);
```

GIN indexes are the right choice for multi-valued data: full-text search,
JSONB, arrays, and hstore. They're fast for reads but slower to update than
B-tree.

### GiST (Generalized Search Tree)

```sql
-- Range and spatial data
CREATE INDEX ix_bookings_during ON bookings USING gist (during);

-- Required for exclusion constraints
-- (see exclusion constraint examples above)
```

GiST supports range overlap, spatial queries (PostGIS), and nearest-neighbor
search. It's the index type behind exclusion constraints.

### When NOT to add an index

- Tables under a few thousand rows — sequential scan is often faster
- Columns with very low cardinality (e.g., boolean) — an index won't help
  unless combined with a partial index predicate
- Write-heavy tables where reads are rare — indexes slow every INSERT/UPDATE
- Columns never used in WHERE, JOIN, or ORDER BY

Use `EXPLAIN ANALYZE` on actual queries to verify an index helps before adding
it.

## Table Design Principles

### One fact, one place (normalize first)

Start with Third Normal Form (3NF). Every non-key column depends on the key,
the whole key, and nothing but the key. Normalization prevents update anomalies
and reduces storage. Denormalize only when you have measured performance data
showing a join is a real bottleneck — and document the tradeoff.

```sql
-- WRONG — denormalized, update anomalies
CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL,
    customer_name text NOT NULL,  -- duplicated from customers
    customer_email text NOT NULL, -- duplicated from customers
    total numeric(12,2) NOT NULL
);

-- CORRECT — normalized
CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL REFERENCES customers(id),
    total numeric(12,2) NOT NULL
);
```

### Junction tables for many-to-many

```sql
CREATE TABLE product_categories (
    product_id bigint NOT NULL REFERENCES products(id) ON DELETE CASCADE,
    category_id bigint NOT NULL REFERENCES categories(id) ON DELETE CASCADE,
    PRIMARY KEY (product_id, category_id)
);
```

Use composite primary keys on junction tables — no surrogate `id` column
needed. If the junction carries its own attributes (e.g., `assigned_at`,
`role`), it's becoming an entity in its own right and may warrant its own `id`.

### Soft delete — think twice

```sql
-- Common pattern, but problematic
ALTER TABLE users ADD COLUMN deleted_at timestamptz;
```

Soft delete adds complexity to every query (forgotten `WHERE deleted_at IS NULL`
leads to showing deleted data). Consider these alternatives:
- **Archive table**: move deleted rows to a separate table
- **Hard delete** with an audit log: delete the row, record the event elsewhere
- **Status column**: if "deleted" is just one of many states, model it as such

If you do use soft delete, create a partial index for active rows and enforce
unique constraints only on non-deleted rows.

### Audit columns

```sql
-- Standard audit columns on every table
created_at timestamptz NOT NULL DEFAULT now(),
updated_at timestamptz NOT NULL DEFAULT now()
```

Add `created_at` and `updated_at` to every table. Use a trigger to auto-update
`updated_at`:

```sql
CREATE OR REPLACE FUNCTION update_updated_at()
RETURNS trigger AS $$
BEGIN
    NEW.updated_at = now();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Apply to each table
CREATE TRIGGER trg_orders_updated_at
    BEFORE UPDATE ON orders
    FOR EACH ROW EXECUTE FUNCTION update_updated_at();
```

### Partitioning

Partition tables when they grow into hundreds of millions of rows and queries
consistently filter on the partition key. Not before.

```sql
-- Range partitioning by time (most common)
CREATE TABLE events (
    id bigint GENERATED ALWAYS AS IDENTITY,
    event_type text NOT NULL,
    payload jsonb NOT NULL DEFAULT '{}',
    created_at timestamptz NOT NULL DEFAULT now()
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2025_q1 PARTITION OF events
    FOR VALUES FROM ('2025-01-01') TO ('2025-04-01');
CREATE TABLE events_2025_q2 PARTITION OF events
    FOR VALUES FROM ('2025-04-01') TO ('2025-07-01');
```

Partition key must appear in the primary key. Partitioning helps with:
- Dropping old data quickly (`DROP TABLE` vs mass `DELETE`)
- Partition pruning for time-range queries
- Parallel scans across partitions

### Schemas for namespacing

```sql
-- Separate concerns into schemas
CREATE SCHEMA auth;
CREATE SCHEMA billing;
CREATE SCHEMA analytics;

CREATE TABLE auth.users (...);
CREATE TABLE billing.invoices (...);
CREATE TABLE analytics.page_views (...);
```

Use schemas to organize large databases by domain. Set `search_path` in the
application to control which schemas are visible without qualification.

## Domains for Reusable Types

```sql
-- Define once, reuse everywhere
CREATE DOMAIN email_address AS text
    CONSTRAINT ck_email_format CHECK (VALUE ~* '^[^@]+@[^@]+\.[^@]+$');

CREATE DOMAIN positive_amount AS numeric(12, 2)
    CONSTRAINT ck_positive CHECK (VALUE > 0);

-- Use in table definitions
CREATE TABLE invoices (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_email email_address NOT NULL,
    total positive_amount NOT NULL
);
```

Domains encapsulate a base type with constraints. They keep validation
consistent across tables and reduce duplication.

## Migration Best Practices

### One concern per migration

Each migration file should do one thing: add a table, add a column, create
an index. This makes rollbacks predictable and reviews easy.

### Non-breaking changes first

When modifying production schemas:
1. Add new columns as nullable (or with defaults)
2. Deploy application code that writes to both old and new columns
3. Backfill existing rows
4. Add NOT NULL constraint
5. Deploy application code that reads from new columns
6. Drop old columns in a later migration

### CREATE INDEX CONCURRENTLY

```sql
-- WRONG — locks the table for the entire build
CREATE INDEX ix_orders_customer ON orders (customer_id);

-- CORRECT — non-blocking (requires running outside a transaction)
CREATE INDEX CONCURRENTLY ix_orders_customer ON orders (customer_id);
```

Always use `CONCURRENTLY` for indexes on production tables. It takes longer
but doesn't block reads or writes. Note: most migration tools run inside
transactions — you may need to run concurrent index creation as a separate
step.

### Add NOT NULL safely

```sql
-- For new columns on existing tables, add with a default then constrain
ALTER TABLE orders ADD COLUMN priority smallint DEFAULT 0;
-- Backfill if needed
UPDATE orders SET priority = 1 WHERE is_urgent;
-- Then add the constraint (PostgreSQL 12+ validates existing rows efficiently)
ALTER TABLE orders ALTER COLUMN priority SET NOT NULL;
```

## Common Anti-Patterns

| Anti-pattern | Problem | Fix |
|-------------|---------|-----|
| Entity-Attribute-Value (EAV) | Loses type safety, no constraints, terrible query performance | Use proper columns, JSONB for genuinely dynamic data, or table inheritance |
| `varchar(255)` everywhere | Cargo cult from MySQL; no PostgreSQL benefit | Use `text` with check constraints where needed |
| No foreign keys ("for performance") | Orphaned rows, broken relationships, harder debugging | FK overhead is minimal; always use them |
| `float` for money | Binary floating point can't represent 0.10 exactly | `numeric(p,s)` or integer cents |
| Timestamp without timezone | Silent timezone bugs when servers or clients differ | Always use `timestamptz` |
| Overindexing | Wastes storage, slows writes, confuses the planner | Index based on measured query patterns |
| Single `status` column doing too much | One column tracking 12 states with complex transitions | Separate boolean flags or a state machine with a dedicated table |
| Storing comma-separated values | Can't index, can't join, can't constrain | Use arrays, JSONB, or a junction table |
| God tables with 40+ columns | Hard to maintain, wide rows hurt cache efficiency | Split into related tables; use 1:1 relationships |
| Missing indexes on foreign keys | Slow cascading deletes and joins | Index every FK column |

## Extension Awareness

PostgreSQL's extension ecosystem is a major strength. Know the key ones:

| Extension | Use for |
|-----------|---------|
| `uuid-ossp` or `pgcrypto` | UUID generation (`gen_random_uuid()` built-in since PG 13) |
| `btree_gist` | Exclusion constraints combining equality with range overlap |
| `pg_trgm` | Trigram-based fuzzy text search and LIKE/ILIKE indexing |
| `citext` | Case-insensitive text type (alternative to `lower()` indexes) |
| `hstore` | Simple key-value pairs (consider JSONB for new projects) |
| `postgis` | Geospatial data types and queries |
| `pg_stat_statements` | Query performance monitoring |

Enable extensions explicitly:
```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```
